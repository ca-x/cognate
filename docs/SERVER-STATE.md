# 服务端状态与凭据（开发中）

`internal/server/state` 是独立于客户端状态库的 ent + entsqlite 服务端存储。`cmd/skillhub-server` 已接入本地账号、OIDC、Connect 认证和 GitHub Lists API，并嵌入 React 管理面板。`CreateUser` 只建立内部用户标识，不提供身份认证；HTTP 调用从已签名会话解析不可变用户 ID，不信任请求身份头。OIDC 身份以 issuer + subject 唯一记录，显式绑定须在同一事务核验原会话，见 `docs/OIDC.md`。`viewer_id` 必须由已授权 GitHub 请求验证；底层保存凭据的方法本身不执行网络验证，已接入的 ConnectToken 和 device flow 会先完成 GitHub Lists 读取验证。

实验性本地账号使用 Argon2id 哈希密码，未知用户名也执行密码哈希；同事务创建用户和账号，session 以独立派生密钥签名，仅将随机 token 的摘要存入数据库，支持过期与登出撤销。认证服务初始化校验主密钥与数据库匹配；查询返回后再次检查 session 过期时间，但不保证已开始的业务操作或响应在到期时被撤回。单个认证服务实例最多同时执行两个密码哈希，超限立即拒绝，不构成速率限制。注册冲突会暴露用户名是否已存在。尚无跨实例或按来源的限流、账号禁用与改密、认证代次、session 清理或时钟回拨/数据库回滚防护；因此不能将该 handler 暴露于生产网络。接入服务前还必须实现 TLS 或明确定义的可信反向代理边界，并禁止记录密码、Authorization 和请求体。当前 handler 忽略转发身份头，设置响应 `no-store` 和消息大小限制；不能由此推断完整服务已具备上述安全能力。

存储调用方必须提供独立保管的 32 字节随机主密钥，缺失时拒绝打开；不会生成或写入密钥。GitHub 凭据在进入 SQLite 前以 AES-256-GCM 加密，随机 nonce 随密文保存；版本、用途、用户、GitHub viewer、OAuth client、密钥标识和凭据代次作为关联数据。数据库元数据绑定密钥标识和 AEAD 验证值；无元数据的旧库只有在所有现有凭据都通过认证后才能采用当前密钥。密钥标识为主密钥的 SHA-256，密钥必须具有足够随机性，不能使用密码或低熵值。普通覆盖要求先认证现有密文及匹配密钥、状态与代次；错误密钥不能覆盖已有记录或向同一库新增另一密钥的凭据。每个主密钥必须遵守随机 nonce 模式的使用上限，尚未实现用量统计、密钥轮换或旧密钥迁移。数据库 schema 迁移在密钥校验前执行，校验失败不代表 schema 完全未变。

SQLite 使用需求指定的 WAL 和 `synchronous(NORMAL)`。已测试主库及 WAL 不含测试明文凭据，但尚未实现在线备份、恢复或历史数据清理；密钥、明文内存、进程与外部日志仍需保护。AEAD 不防整库回滚，恢复旧数据库快照后不得自动信任旧授权或重放 refresh token。断电和操作系统崩溃持久性尚未验证，不能由进程退出测试推断。

Unix 数据目录须为当前用户拥有的私有目录，其路径链不得有符号链接或非 sticky 的其他用户可写祖先；数据库及 SQLite sidecar 须为当前用户拥有的私有单硬链接普通文件。检查仍依赖可信、稳定路径和遵守协议的进程，无法消除检查后由同 UID 非协议主体替换文件的 TOCTOU。Windows 服务端存储安全检查尚未实现，当前拒绝运行；交叉编译不代表原生支持。

服务入口创建数据目录前先验证已存在的全部祖先，再通过 `os.Root` 逐级创建；不会先经符号链接创建目录再报错。安全目录操作及 SQLite 必须使用本地句柄语义，skill 文件内容与后续备份仍通过 Afero 接口。

`GitHubCatalog` 在同一数据库事务及凭据行锁协议下读取列表和去重仓库，避免拼接两次查询的不同订阅状态；返回的 `ValidUntil` 不晚于当前观察期限和 token 期限。面板到该时间即隐藏旧内容，并定期或在重新聚焦时刷新。

`BeginListSync` 在事务内为指定用户与凭据代次增加持久同步代次；`ReadListSync` 首先事务性认领一次性读取 ID、认证客户端凭据，再发起 GitHub 读取并返回绑定票据的不透明结果；同一票据不能重复读取。`CommitListSync` 只接受该结果，并在同一事务核对用户、viewer、密钥、凭据及同步代次、读取 ID 和未应用标记，认证解密后确认 GitHub 客户端实际凭据，才运行调用方的应用回调。回调失败则应用与已应用标记一起回滚；成功后重复提交被拒绝。读取失败需重新申请同步票据。该机制防止遵守协议的多个进程提交被后续同步或重新授权取代的结果，也避免把旧快照配给新票据；但不验证 GitHub 跨页快照一致性，订阅和可见性策略见下文。

实验性 catalog 按服务端用户和 GitHub viewer 隔离 list、repository 与 membership，使用 GitHub node ID 而非可变名称作为身份。数据库触发器拒绝跨用户或跨 viewer 的 membership，并禁止修改 list/repository 的归属；初始化时先检查已有关系。同步先发现列表，用户选择订阅后，后续完整同步才将订阅列表的仓库标记为可见；多个订阅中的相同仓库只返回一次。切换订阅会在同一事务推进同步代次并隐藏旧成员。缺失列表或成员保留为历史记录，但不会由当前查询返回；失败或取消不将它们解释为删除。

新的同步开始时先隐藏当前 viewer 的旧列表；只有完整提交后重新显示。更换凭据代次、token 过期、viewer 切换或观察过期也使旧列表和仓库不可见，重新验证后才恢复。观察时间从 GitHub 读取开始计算，默认最长 1 小时，`OpenWithOptions` 可设为大于零、最多 24 小时；策略经 AEAD 绑定到数据库，同库实例必须一致，修改策略的迁移尚未实现。查询返回前再次检查 token 与观察期限，时间落在未来时不视为有效。该期限依赖可信、非倒退的系统时钟；时钟回拨可能让此前过期的观察重新进入期限，目前没有持久时间水位保护。GitHub 侧撤权无法即时通知；时钟正常时，两次成功同步之间仍可能存在不超过配置期限的可见窗口。尚无定时任务、历史清除或生产 API，服务端不能绕过这些查询直接读取历史记录或缓存。

持久化的 refresh 凭据目前不会通过普通读取返回；跨进程刷新锁、持久刷新意图、响应丢失处理和恢复尚未接入。即使进程内 GitHub 内核支持刷新，也不得绕过这些未完成的边界对持久凭据直接刷新。
